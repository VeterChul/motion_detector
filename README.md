# cctv

Система видеонаблюдения с детекцией движения и уведомлениями.

## Архитектура

Выбрана микросервисная архитектура. Система разбита на четыре контейнера, каждый из которых отвечает за одну задачу и не знает лишнего о других.

## Контейнеры

**mediamtx** — медиасервер. Единственный компонент, работающий с камерой и микрофоном. Захватывает поток через ffmpeg, кодирует видео и звук одним процессом (поэтому они синхронизированы), ведёт непрерывную запись архива в fMP4 с автоудалением старых файлов, отдаёт RTSP-поток для детектора и предоставляет Playback API для получения произвольных интервалов архива. Ничего не знает о движении, событиях и уведомлениях.

**detector** — Python-контейнер. Подключается к RTSP-потоку mediamtx, анализирует кадры (MOG2, маски игнорируемых зон, подтверждение «3 из 5»), публикует в MQTT только сигналы движения и heartbeat. Не знает про Telegram, события, части видео и нарезку. Его роль — превратить видеопоток в поток маленьких временных меток «здесь было движение».

**mail** — Python-контейнер. Отвечает за всю логику уведомлений и общения с пользователем. Слушает MQTT, ведёт состояние текущего события, собирает видео через Playback API mediamtx, режет на части, отправляет в Telegram, реализует бота (пауза, статус, `/snap`, `/clip` и т.д.). Не знает про OpenCV, MOG2, маски и RTSP. Название нейтральное: Telegram — просто текущий канал доставки, при необходимости заменяется без изменения остальных контейнеров.

**mosquitto** — MQTT-брокер. Единственный канал связи между detector и mail.

**autoheal** — перезапускает контейнеры, у которых healthcheck перешёл в unhealthy. Docker Compose этого сам не делает.

## Почему такое разделение

Запись архива, детекция движения и логика уведомлений — три разные задачи с разными зависимостями и разными требованиями к надёжности. Разделение даёт независимые перезапуски (правите порог детекции — не трогаете бота), заменяемость канала уведомлений и более поддерживаемый код за счёт чёткой границы ответственности.

## Почему MQTT

detector и mail связаны асинхронно через брокер, а не напрямую по HTTP. Это даёт развязку: detector публикует событие, не заботясь о том, доступен ли mail прямо сейчас. Если mail перезапускается или обновляется, события не теряются — брокер сохранит их и доставит после восстановления подписчика. Для системы, где пропущенное движение означает потерянное уведомление, это критично.

MQTT выбран вместо Kafka и подобных решений, потому что задача — обмен мелкими сообщениями между двумя сервисами с одной камерой. Kafka избыточна (JVM, ZooKeeper, сотни мегабайт памяти), а Mosquitto — это образ в 5 МБ с минимальным потреблением ресурсов. QoS 1 обеспечивает доставку, retained-сообщение с текущим состоянием позволяет mail при старте сразу узнать, что происходит у detector.

## Как проходит событие

Детектор подтверждает движение и публикует `motion_started` с временной меткой. Mail создаёт событие, отправляет фото и головное сообщение в Telegram с кнопками, планирует первую часть видео `[t−60с, t+30с]`. Через ~35 секунд забирает интервал через Playback API mediamtx и отправляет. Пока движение продолжается, детектор обновляет last_motion, mail собирает и отправляет следующие части по 120 секунд. Когда тишина длится 60 секунд, событие закрывается, отправляется последняя часть, подпись головного сообщения обновляется.

Ключевой принцип: архив пишется всегда, детектор только фиксирует время. «Минута до движения» физически уже лежит в архиве к моменту срабатывания, её не нужно буферизовать заранее. Поэтому при отключении питания через 40 секунд после начала движения часть 1 уже в Telegram.
